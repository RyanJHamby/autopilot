# Ryan's guardrails are strong locally but advisory and unportable

Ryan's setup already has the right instincts (hooks, signed commits, branch protection, a constitution, a vault, a journal), but measured against the "mistake-proof, automatic, portable" requirement, its weakest property is **enforcement authority and rebuildability, not the number of rules**. The strongest documented enforcement layers are server-side GitHub rules with admin bypass off, and CI. Claude Code managed settings come next. Ryan's rules mostly sit in layers the docs treat as advisory: user hooks (fail open unless they exit 2), prose constitutions and CLAUDE.md, and local git hooks (skippable with the no-verify flag). Claude Code's own docs say prompt and CLAUDE.md instructions "don't change what Claude Code allows" ([Permissions](https://code.claude.com/docs/en/permissions)), so the constitution's "never edit .github/, .claude/, AGENTS.md" is a request, not a lock, unless something else backs it. The seven highest-value gaps: (1) the constitution and `policy/deny.json` have no confirmed enforcement layer; (2) the server-side layer is unverified for a personal GitHub account, and rulesets, bypass lists and required checks have documented holes; (3) a new laptop cannot be rebuilt from repos alone (no Brewfile, `~/.claude/CLAUDE.md` and `settings.json` not mirrored, manual steps unwritten, auto-memory per-machine); (4) there is no self-test that proves guardrails still work (hooks fail open silently); (5) the knowledge vault has threads but no decision-record convention, no where-does-it-go rule and no staleness metadata; (6) cost control is a run-point proxy whose weights look stale against the 2026-10-29 price table and has no hard cap layer; (7) employer-IP separation depends on a contract Ryan has not been verified to have read, in a state the notes do not know. Evidence is uneven. Enforcement, Claude Code workflow and cost mechanics are well sourced from vendor docs. Knowledge-system practice rests on practitioner assertion, and marketing/sales and legal are thin. Researchers had page fetching but no web search, and many guessed URLs 404'd.

## Where each kind of information goes, and how knowledge changes over time

No published rule covers all four categories (the notes say so explicitly), so the rule below is assembled from fragments and is inference, not a standard. Its ingredients are documented. Decision records belong only to choices that affect structure, key quality attributes, or are hard to reverse ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). Claude Code separates human-written instructions (CLAUDE.md) from model-written learnings (auto memory) ([memory docs](https://code.claude.com/docs/en/memory)). Anthropic treats persisted agent notes as working memory outside the context window ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

| Kind of information | Where it goes | Mutability | Enforced by |
|---|---|---|---|
| What happened, including failures and dead ends | `docs/journal.md` via `pow log` (per repo); vault journal for non-repo work | Append-only | Advisory today (prose in AGENTS.md); could be CI-checked for PRs touching decision paths |
| Why X was chosen over Y (hard to reverse, structural, or spend-a-token) | Numbered decision record, ~10 lines: title, status, date, context, decision, consequences, confidence | Immutable once accepted; change by a new record that supersedes | Lint in CI or `doctor` (front matter, unique numbers, supersede links resolve) |
| Current truth that can rot (prices, tool versions, "we use Postgres", legal status) | Fact note with `as_of` and `review_by` | Mutable, dated | Lint finds overdue `review_by` |
| How a system works now, plus rules an agent must obey in this repo | That repo's AGENTS.md, `.claude/`, spec files, under 200 lines | Living, versioned with the code | Deny rules, hooks, CI for anything that cannot have exceptions |
| Cross-repo or personal knowledge | Vault, flat folders, ISO dates, properties for categories | Mixed | Index file kept small and generated |
| Agent-learned preferences and pointers | Auto-memory MEMORY.md as a pointer index, detail in topic files | Pruned | Built-in 200-line or 25KB load cap (content past it is silently dropped) |

The temporal scheme has two halves, both supported separately. For choices, use supersession: Nygard keeps the old record and marks it superseded because "it's still relevant to know that it was the decision" ([Nygard](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)), Microsoft says never edit accepted records ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)), and MADR's front matter carries `status: superseded by ADR-0123` and a date ([MADR](https://adr.github.io/madr/)). For facts, use dated metadata: Microsoft's own pages carry `ms.date` and `ms.update-cycle: 1095-days`, and Graphiti's design principle is that old facts are "invalidated, not deleted" ([Graphiti](https://github.com/getzep/graphiti)). The proposed front matter, `status`, `supersedes`/`superseded_by`, `as_of`, `review_by` (plus `confidence` on decisions, per Microsoft's advice), is the cheap markdown approximation of both. It is my inference. No source measured it, and the notes found no outcome evidence that ADRs or review dates work; support is practitioner assertion. Graphiti-style bitemporal graphs need a graph database and an OpenAI key by default ([Graphiti](https://github.com/getzep/graphiti)) and are overweight for a flat markdown vault. Retrieval should stay grep or SQLite FTS, which `cct find` already is. Anthropic favors a small always-loaded index plus just-in-time retrieval, and the Claude Code creator reports agentic search beat embedding RAG "by a lot" on internal judgment, not a benchmark ([Latent Space](https://www.latent.space/p/claude-code)).

Two cautions follow from the failure modes. Every extra layer (nested taxonomy, vector index, graph DB, long instruction file) is something to keep in sync, so cap and generate indexes rather than hand-maintain them. And one source disagreement matters for design: Nygard and Microsoft want immutable records, while Oxide lets published RFDs be updated and has a "committed" state ([Oxide RFD 1](https://rfd.shared.oxide.computer/rfd/0001)). The reconciliation is append-only records for choices and living docs for how things work now. Oxide's benefit also comes from colleague review, which a solo user lacks.

## Knowledge and decisions: the vault stores threads, not truth

**Best practice.** Short numbered append-only records with a supersession link, a small always-loaded index, flat dated markdown, retrieval by grep, and a periodic audit. Claude Code ships `/doctor prompt-audit`, which flags stale references and contradictions in instruction files ([memory docs](https://code.claude.com/docs/en/memory)). **Evidence:** moderate for the mechanisms, none for effectiveness; Amazon memos, Basecamp, PARA and Zettelkasten were not fetched. **Ryan's state:** `cct` is a capable thread store (FTS, handoffs, signed sync to a gcrypt remote). The vault has dated notes and a changelog, but no knowledge index, no decision-record convention and no temporal metadata. Auto-memory uses the documented pointer-index design, which matches Anthropic's pattern. The `pow log` journal covers "what happened," not "what is currently decided." **Gap: high value, low effort.** Retrieval already exists, so the missing piece is a convention plus a lint. **Fix:** add `decisions/NNNN-title.md` (per repo for repo choices, in the vault for cross-repo ones) with the front matter above; add a `cct doctor` check (front matter present, supersede links resolve, overdue `review_by`, index under size cap); add the where-it-goes table to the vault README. **Enforcement:** advisory until the lint runs in CI for repos and as a scheduled job for the vault; the vault has no CI, so state plainly that vault lint is local and can be skipped. **New laptop:** automatic for vault content (it comes back with `cct restore`), but see portability below for what does not.

## Tool and stack selection: a cheap rule, with no outcome evidence

**Best practice.** McKinley's innovation tokens, about three per company, spent only where differentiating ([Choose Boring Technology](https://mcfunley.com/choose-boring-technology)), plus Bezos's one-way versus two-way doors, where most decisions are reversible and should be fast ([Amazon 2016 letter](https://www.sec.gov/Archives/edgar/data/1018724/000119312516530910/d168744dex991.htm)). Shape Up's circuit breaker cancels projects that do not ship in one cycle by default ([Shape Up](https://basecamp.com/shapeup/1.2-chapter-03)). The Thoughtworks Radar's Adopt/Trial/Assess/Caution rings, reviewed twice a year, are a ready template for a personal list ([Radar FAQ](https://www.thoughtworks.com/radar/faq)). **Evidence:** the frameworks are well sourced; the notes found **no empirical study** that written stack rationale improves outcomes, could not verify any named founder's stack, and found nothing on language choice for systems or data infrastructure. The two usage surveys are populations, not founder practice. **Ryan's state:** policy/portfolio.yaml tiers repos A/B/C and repo.yaml has modes, which is a portfolio mechanism; there is no stack-selection record and no tool list (UNVERIFIED beyond the coordinator's survey). **Gap: medium value, low effort.** **Fix:** make the ADR template's context section carry McKinley's question ("what exactly is too hard with what I have?") and a token/door tag; keep a one-file personal Radar with `review_by` six months out; treat appetite as a fixed calendar budget per repo with "ship or archive" as default, logged as a record. Tiering and cadence are my suggestions, not sourced. **Enforcement:** advisory, and that is acceptable here because these are two-way doors. **New laptop:** automatic if the files live in a synced repo.

## Model and token spend: a proxy that has drifted from the price table

**Best practice.** Haiku for simple and subagent work, Sonnet for daily coding, Opus for complex reasoning, Fable for the hardest tasks, and `opusplan` for plan-then-execute ([Model config](https://code.claude.com/docs/en/model-config)). Subagents inherit the session model unless set, so switching to Opus before delegating makes subagents Opus too ([Costs](https://code.claude.com/docs/en/costs)). Effort is a second dial, and medium is the default on the 5.5 models. Prompt caching is the biggest lever, with reads at 0.05 to 0.1x base input, and model switches and MCP changes bust it ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). The documented hard caps are Console org and workspace limits, SDK `max_budget_usd` and `maxTurns`, subagent depth and concurrency limits, and LiteLLM per-key budgets (which are silently unenforced without a database) ([Rate limits](https://platform.claude.com/docs/en/api/rate-limits); [SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [LiteLLM](https://docs.litellm.ai/docs/proxy/users)). Costs shown in Claude Code are client-side estimates, and the SDK docs say not to trigger financial decisions from them ([SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)).

Pricing, fetched 2026-10-29 from Anthropic's page ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)), per million tokens input/output: Haiku 5.5 $0.10/$0.50 (repriced 5x above a 100K-token prompt), Sonnet 5.5 $2/$10, Opus 5.5 $4/$20, Fable 5.1 $10/$50. Output is 5x input on every current tier (derived).

**Evidence:** strong on mechanics. Savings numbers are vendor-run or old-generation. RouteLLM and FrugalGPT report large savings on chat benchmarks with GPT-4-era models, and Anthropic's advisor result (about 12% cheaper, +2.7 points on SWE-bench Multilingual) used Claude 4.6-generation models ([advisor strategy](https://claude.com/blog/the-advisor-strategy)). There are **no independent coding-agent routing measurements** and no 5.5-generation pairing numbers. **Ryan's state:** the autopilot cost spec uses run-point weights of haiku 1, sonnet 3, opus 15 times a turn cap, explicitly a proxy with no dollar claims, which is honest. **Finding (inference from the table):** those weights match the old-generation input price ratios, not the 2026-10-29 table, where Sonnet 5.5 is 20x Haiku 5.5 and Opus 5.5 is only 2x Sonnet 5.5 on input. The weights therefore under-count Sonnet versus Haiku and over-count Opus versus Sonnet. Plan type is UNVERIFIED; on a subscription, dollars are not metered and the real limits are the five-hour and weekly windows ([Costs](https://code.claude.com/docs/en/costs)), so Console spend limits would not apply to subscription use. **Gap: medium-high value, medium effort.** **Fix:** (1) move the weights into `policy/pricing.yaml` carrying `as_of` and `review_by`, with a source URL, so the next price change is a scheduled review rather than a surprise; (2) every unattended `claude -p` or SDK run gets `--max-budget-usd` and a turn cap enforced by the runner script, not by prose; (3) define explicit `model:` frontmatter for each role in `.claude/agents/` (triage on Haiku, per the docs' guidance); (4) if any API key is in use, set a Console monthly limit well below the tier cap and a separate workspace per agent; (5) log `total_cost_usd`/`modelUsage` per PR from the SDK and reconcile weekly against the Console, treating it as an estimate ([SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)); (6) watch the cache-hit line in `/usage`. Items 1, 3 and 5 are my synthesis; 2 and 4 are documented controls. **Enforcement:** the runner and SDK budget cap is enforced for those runs but bypassable by running Claude interactively; Console limits are server-side. **New laptop:** automatic only if the runner and pricing file are in a repo and the Console limit already lives on the account.

## Agentic workflow and portability: repo-level is portable, user-level is not

**Best practice.** Anthropic and practitioners converge on a short instruction file with only what the agent cannot infer, deterministic enforcement for anything with no exceptions ("if you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook"), a verification command the agent can run, plan separated from execution, one isolated checkout per parallel agent, and human review as the bottleneck ([best practices](https://code.claude.com/docs/en/best-practices); [Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey); [Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)). Hashimoto's rule is that each agent error should change the setup so it cannot recur. The autonomy checklist includes "the one branch it may push to" ([best practices](https://code.claude.com/docs/en/best-practices)), which is what `agent/*` branches do. AGENTS.md is read by Codex, Cursor, Copilot and others, so AGENTS.md as the source with a thin CLAUDE.md import is the portable choice ([agents.md](https://agents.md)), and Ryan's repo already does this. **Evidence:** vendor docs plus a handful of practitioner posts; no controlled studies of these practices, and the Pragmatic Engineer survey (906 self-selected readers) shows adoption, not effectiveness ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/ai-tooling-2026)). **Ryan's state:** repo-level portability is good: roles in `.claude/agents`, specs with acceptance commands, a constitution and a repo.yaml all travel with `git clone`. User-level portability is weak. Three documented facts bite. First, auto-memory lives under `~/.claude/projects/<path>/memory` and the notes found no sync story, so the feedback entries in MEMORY.md would not reappear on a new machine (inference from absence; verify). Second, cloud sessions read only the committed repo, not `~/.claude` or `settings.local.json` ([settings](https://code.claude.com/docs/en/settings)), so any guardrail that exists only as a user hook is absent in cloud runs. Third, `cct` transcripts are not pushed, so a new laptop with only the gcrypt remote gets threads, notes and handoffs but not full transcripts, because `cct restore` copies local vault copies back (derived from the coordinator's facts). The vault's only remote being GPG-encrypted also makes the GPG key a single point of failure (inference; backup of the key is a manual step not in any runbook).

The plugin marketplace is Anthropic's own answer for personal cross-repo skills: a git repo with `.claude-plugin/marketplace.json`, registered by `extraKnownMarketplaces` and `enabledPlugins`, installable on any machine in two CLI commands, with a seed directory for containers ([plugin marketplaces](https://code.claude.com/docs/en/plugin-marketplaces); [plugins for organizations](https://code.claude.com/docs/en/plugins/org)). For remote access, Remote Control drives a local session from the phone but goes offline if the process or terminal stops, uses outbound HTTPS only, and needs a Pro/Max/Team/Enterprise login rather than an API key ([Remote Control](https://code.claude.com/docs/en/remote-control)); Tailscale SSH on macOS works only with the open-source `tailscaled`, not the GUI app ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)). Ryan's laptop is the only host, with sleep disabled; the notes sourced nothing on wake-on-LAN or always-on host choices. **Gap: medium value, medium-high effort; defer the always-on host until the enrollment work below is done.** **Fix:** put personal skills and the `/pause` command in a private marketplace repo; document which state is per-machine on purpose (`~/.claude.json`, which the docs say is self-written and not to be synced); decide explicitly whether to back up auto-memory (a nightly copy into the vault is the simplest option, my suggestion); and for cloud or Actions runs, commit the needed deny rules to each repo's `.claude/settings.json`, where they apply immediately ([settings](https://code.claude.com/docs/en/settings)).

## Enforcement and enrollment: authority ranking and where Ryan sits on it

This is the core-requirement axis. The ranking below is my inference from the cited documentation, and the notes say so.

| Rank | Layer | What the docs say | Bypass | Reappears on a new machine? |
|---|---|---|---|---|
| 1 | GitHub ruleset or protected branch, admin bypass off, checks pinned to the Actions app, signed commits required | Admins are exempt by default; "Do not allow bypassing" applies rules to them; bypass lists need an organization-owned repo ([protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)); rulesets are listed as Team/Enterprise ([rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)) | Ryan as repo admin if bypass is on; otherwise only by editing the setting (needs 2FA or key) | Yes, it lives on the server, but applying it to each new repo is a script run (`protect-repo.sh`), not automatic |
| 2 | CI | Required checks pass if skipped or neutral, so a path-filtered required job passes silently ([protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)); a workflow file is editable in a PR | Anyone who can edit `.github/` unless that path is protected | Yes (server) |
| 3 | Claude Code managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json`) | Highest precedence; `allowManagedHooksOnly`, `disableBypassPermissionsMode`; "a developer who is an administrator on the machine can edit the managed source itself" ([managed settings](https://code.claude.com/docs/en/managed-settings)) | A local admin (Ryan with sudo); not the agent running as the user (inference) | No, needs sudo install on each machine |
| 4 to 5 | Project `.claude/settings.json` deny rules; project and user hooks | Deny rules apply immediately; hooks fail open unless exit 2 (exit 1 is non-blocking), timeouts do not block, `onFailure: "block"` makes them fail closed ([Hooks](https://code.claude.com/docs/en/hooks)); deny rules do not match a program invoked by path or inside `sh -c` ([Permissions](https://code.claude.com/docs/en/permissions)) | The agent can edit non-protected files; Ryan can edit anything | Project layer yes via clone; user hooks only after `bootstrap.sh` |
| 6 | Local git hooks | pre-commit, commit-msg and pre-merge-commit hooks "can be bypassed with the `--no-verify` option"; pre-commit hooks are not active after clone ([githooks](https://git-scm.com/docs/githooks); [pre-commit](https://pre-commit.com/)) | Anyone, trivially | No unless `init.templateDir` is configured |
| 7 | CLAUDE.md, AGENTS.md, the constitution as prose | Context, not enforcement ([memory docs](https://code.claude.com/docs/en/memory)) | The model can disregard; anyone | Yes via clone, but advisory |

Mapped to Ryan: the admin repo's hooks (destructive ops, signing and no-verify, secrets, home-dir gate) are layer 5 and are tested by `run_tests.sh`; the 2b event shows they fire (a write containing the skip-hooks text was blocked), though that is a text match, not intent analysis, and the docs warn the `if` filter is best-effort. `protect-repo.sh` is layer 1, with unknown strength. The constitution and `policy/deny.json` are layer 7 unless something wires `deny.json` into layer 3 or 4 (not confirmed). **Four documented holes deserve fixes.** (a) Hooks fail open, so each should exit 2 explicitly and set `onFailure: "block"` where the installed version supports it (v2.1.295 or later per the hooks docs). (b) A required `ci` check that is conditionally skipped passes, so keep it always-running or use a summary job. (c) CODEOWNERS with a sole owner cannot approve their own PR (flagged as unresearched in the notes), so test the interaction with required review before relying on it. (d) The sandbox reads `~/.ssh` and `~/.aws/credentials` by default unless `denyRead` is added, and hook scripts and statusline commands run unsandboxed ([Sandboxing](https://code.claude.com/docs/en/sandboxing)); add explicit `Read` deny rules for secrets (`.claudeignore` has no effect). The incidents the notes found (Replit's database deletion during a code freeze, Antigravity's Turbo mode wiping a drive) are press reports of user claims, and share one root: the control was an instruction or an unattended mode, not an enforced boundary ([The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/); [The Register](https://www.theregister.com/2025/12/01/google_antigravity_wipes_d_drive/)).

**The honest limit.** Ryan is the admin on his laptop and on his GitHub account, so nothing on the machine is unbypassable by him. The achievable goal is mistake-proofing against the agent and against forgetting, not against deliberate override. The real "force me to obey" layer is the server with bypass off and a hardware-key barrier to changing it. Whether that is available on a personal account is **unknown**: the fetched pages did not say, and bypass lists require an organization. A free GitHub organization is a possible workaround, but whether it provides what Ryan needs is unresearched.

**Enrollment.** The documented building blocks are `init.templateDir` plus `pre-commit init-templatedir` (auto-hooks every new clone), template repos (one-time copy, no later sync, silent on whether rulesets copy), copier (re-applies template changes with `copier update`; `check-update --quiet` exits 2 when behind) ([copier](https://copier.readthedocs.io/en/stable/updating/)), and chezmoi (single static binary, templates for per-machine differences, `run_onchange_` scripts that can drive `brew bundle`, password-manager integration) ([chezmoi](https://www.chezmoi.io/why-use-chezmoi/); [macOS guide](https://www.chezmoi.io/user-guide/machines/macos/)). The chezmoi comparison to alternatives is vendor advocacy. No source measured how long solo developers sustain chezmoi, Nix or any alternative; Nix, devcontainers, Ansible, MDM and 1Password/age were not researched. Ryan's `bootstrap.sh`, `new-repo.sh` and `ship.sh` already realize most of the "pit of success" pattern (one script that applies the template, branch protection and hooks). The "managed block plus `ap upgrade`" in AGENTS.md is the right propagation mechanism, which template repos alone lack. What is missing: Brewfile, mirrored `~/.claude/CLAUDE.md` and `settings.json`, a manual-steps runbook, managed-settings install, and any proof that a clean machine ends up correct. The minimum irreducible manual set is, by inference, Apple ID and prerequisites, GitHub authentication with a key, one secret-store unlock, GPG key restore, Tailscale join and a sudo approval; everything else should be scripted. Note a documented trap for the simplest approach (symlinking `~/.claude/settings.json` into a repo): if it points at a read-only or generated file, in-app changes are lost next session ([settings](https://code.claude.com/docs/en/settings)). Either keep it writable from the repo or treat repo changes as the only path.

**Self-healing.** The notes found no built-in scheduled guardrail verification. Because hooks fail open and skipped checks pass, tests must exercise the negative path: attempt a forbidden action in a throwaway repo and assert refusal (unsigned push rejected, protected-path edit denied, skipped-check case failing the summary job). `claude doctor` and `/status` show which settings were dropped and which managed source is active ([settings](https://code.claude.com/docs/en/settings)), and anyone with read access can view active rulesets, so a read-only token can audit them via the API ([rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). A scheduled doctor that opens an issue on drift is the natural design, but it is unsourced design. On behavioral science, the strongest retrieved evidence is the WHO surgical checklist before/after study (death 1.5% to 0.8%, complications 11.0% to 7.0%, 3,733 and 3,955 patients, no concurrent control) ([PubMed](https://pubmed.ncbi.nlm.nih.gov/19144931/)); it does not show that coding guardrails work, and the counter-evidence (Urbach 2014), habit and defaults literature were not retrieved. Do not cite behavioral science for this project.

## Legal and IP: the biggest unquantified risk and the one that cannot be automated

California Labor Code 2870, New York Labor Law 203-f, Washington RCW 49.44.140, Delaware 19 Del. C. 805 and Minnesota 181.78 each void employer invention-assignment clauses for inventions made entirely on the employee's own time without employer equipment, supplies, facilities or trade secrets. All five keep the carve-back: the clause still reaches inventions that relate to the employer's business or actual or demonstrably anticipated R&D, or result from work for the employer ([CA 2870 mirror](https://codes.findlaw.com/ca/labor-code/lab-sect-2870/); [NY 203-f](https://www.nysenate.gov/legislation/laws/LAB/203-F); [WA 49.44.140](https://app.leg.wa.gov/rcw/default.aspx?cite=49.44.140); [DE Title 19](https://delcode.delaware.gov/title19/c008/index.html); [MN 181.78](https://www.revisor.mn.gov/statutes/cite/181.78)). Several were read through summarizing tools or a non-official mirror, so statute text must be re-read at the official site. Illinois failed to fetch, and PA, NJ and TX were not checked. "No statute, relies on contract" for those states is a working assumption, not a finding. The notes also state that these laws speak of "inventions" and do not confirm how courts treat software copyright. **Ryan's state is mostly unknown:** his state, his agreement's terms, any outside-activity clause, and the choice-of-law clause are all UNVERIFIED. What the coordinator did verify is that a Desktop file records the intent to keep side projects off employer hardware, accounts and hours with dated records. That aligns with the statutory test (own time, no employer equipment) and with `pow`'s dated journal, but the notes sourced no law-firm guidance on it, so call it sensible and unsourced. The "relates to employer's business" prong is the widest gate and the least predictable, and a data or infra product adjacent to an employer in the same space is the exposure (inference).

AI adds one concrete, sourced point. On consumer plans (Free, Pro, Max, including Claude Code from those accounts) users choose whether sessions train models, with 5-year retention if opted in; API, Team, Enterprise, Bedrock and Vertex fall under commercial terms where Anthropic "may not train models on Customer Content from Services" ([consumer terms update](https://www.anthropic.com/news/updates-to-our-consumer-terms); [Commercial Terms](https://www.anthropic.com/legal/commercial-terms), page showed an effective date of June 17, 2025; verify current). The implication (inference) is that employer or customer code must never enter a personal consumer account, and the training toggle should be checked once and recorded. On copyrightability, the notes confirm the Copyright Office's Part 2 report exists (January 2025) but could not read its conclusions ([Copyright Office](https://www.copyright.gov/ai/)); Anthropic's output assignment is "its right, title and interest (if any)," so the terms do not settle whether copyright subsists. Draw no conclusion about the copyright status of AI-generated code from this report. Entity guidance is vendor commentary only: Stripe Atlas says professional investors strongly prefer C-corps and YC may require conversion ([Stripe Atlas](https://stripe.com/guides/atlas/llc-vs-c-corp)); nothing covers timing relative to first revenue or whether forming an entity triggers a disclosure duty to the employer. Free templates exist (Common Paper's NDA, Terms, DPA, Design Partner and AI Addendum under CC BY 4.0, [Common Paper](https://commonpaper.com/standards/); Cooley GO's inventions assignment and diligence list, [Cooley GO](https://www.cooleygo.com/documents/)), but fit needs counsel. For licensing only DCO and FSL were fetched ([DCO](https://developercertificate.org/); [FSL](https://fsl.software/)), so license choice is open. The CCPA thresholds ($26.625 million revenue, 100,000 California consumers or households, or 50% of revenue from selling or sharing personal information) make a small B2B founder likely out of scope by its own terms, but the CPI figure may have been adjusted ([CPPA FAQ](https://cppa.ca.gov/faq.html)); contract obligations such as DPAs and security questionnaires arrive first.

**Gap: highest risk, low effort, unautomatable in its core.** **Fix:** (1) Ryan reads his employment agreement this week for invention assignment, outside-activity, confidentiality and AI-tool clauses, and records the date and a summary in a dated decision record; (2) consider a one-time employment-lawyer review before any product work or customer contact; (3) record the facts the statutes turn on (state, hardware, accounts, hours, whether the project relates to the employer) in the repo's journal at project start; (4) add a `doctor` check that side-project repos use the personal git identity and signing key and that Claude is logged in to the personal account with the training setting recorded (inference; no source describes such a check). Enforcement: advisory/self-attested, with signing identity and branch protection as the only mechanical parts. New laptop: the doctor checks reappear with bootstrap; the contract review does not.

## Build order, with how each step is verified

The order puts first what the core requirement needs most: a rebuildable machine, a proof that guardrails work, and the highest-authority layer. Ryan's own working practice (state how success will be verified; plan before multi-file work) applies, so each step below should be proposed and approved before editing. Step 0 can run in parallel.

0. **Verify the unknowns (about an hour; includes the legal read).** Run `gh api` against one repo to see whether the ruleset or branch protection is active, whether bypass is allowed and whether the `ci` check can be skipped; run `claude doctor` and `/status` to see which settings sources and managed settings are active; note the plan type; read the employment agreement and record the date. Verified when each answer is written down in a dated record. This resolves four of the open questions below.
1. **Make the machine rebuildable.** Add a Brewfile; mirror `~/.claude/CLAUDE.md` and `settings.json` into `~/dev/admin` and have `bootstrap.sh` install them; write the manual-steps runbook (GPG key restore and backup, `gh auth`, Tailscale join, sudo prompts); add an auto-memory backup decision. Verified by running bootstrap on a clean macOS user account or VM and diffing the result against the repo copy; success means a second Claude Code session there shows the same hooks and settings in `/status` with no hand edits. Whether chezmoi is worth adopting over plain symlinks stays open; the plain approach fits the existing scripts, and chezmoi's evidence is vendor advocacy.
2. **Write the doctor with negative-path canaries.** `cadmin doctor` checks: hooks present and executable, hook exit codes (feed each the forbidden sample and assert exit 2), settings drift by hash against the repo, `commit.gpgsign` true and key available, ruleset state via `gh api`, `init.templateDir` set. Verified by deliberately breaking each item in a scratch repo and seeing doctor fail with an actionable message (the audit-and-feedback evidence says specificity matters, [PubMed](https://pubmed.ncbi.nlm.nih.gov/22696318/), though effect sizes weren't retrieved).
3. **Close the server-side holes.** Per step 0 findings: bypass off where possible; `ci` made an always-running job or summary job; `.github/` and `.autopilot/` protected by CODEOWNERS plus a path rule; `new-repo.sh` calls `protect-repo.sh` and doctor fails if any repo lacks it. Verified by trying to push an unsigned commit and a direct push to main on a throwaway repo and seeing both rejected, and by opening a PR that skips the check and seeing it block.
4. **Install managed settings from the repo.** Deploy `policy/deny.json` plus `disableBypassPermissionsMode`, deny rules on edits to `.autopilot/**`, `.claude/**`, `AGENTS.md`, `CLAUDE.md`, and `Read` denies for secret paths, with `bootstrap.sh` doing the sudo copy and doctor checking the hash. Verified by a canary where the agent tries an edit to a protected path and a `sh -c`-wrapped destructive command, recording what is and is not blocked (the docs say deny rules miss path-invoked and `sh -c` programs, so document the residual).
5. **Schedule the doctor.** A launchd job locally and a weekly GitHub Action for the server-side audit, both opening an issue on drift. Verified by seeding drift and confirming the issue appears within one cycle.
6. **Add the decision-record and fact-note convention and lint.** Template, where-it-goes table, and lint for front matter, supersede links, `review_by`, and index size. Verified by a seeded broken link and an overdue date failing, and by converting two existing choices (such as the cost weights and the gcrypt vault) into the first records.
7. **Fix cost control.** `policy/pricing.yaml` with `as_of`/`review_by`; budget and turn caps in the runner; per-role models; per-PR cost logging. Verified by an unattended run that deliberately exceeds a tiny budget and is cut off, and a weekly reconciliation against the Console or `/usage`.
8. **Defer:** always-on host, private plugin marketplace, personal Radar, outbound compliance gate (until a product exists).
